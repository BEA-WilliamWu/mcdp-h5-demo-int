The provider-owned DSP source is restored to b5e5eec. No DSP application/configuration changes are delivered.
The CM code does not invent protocol, queryOnly, credentialStatus, requestId fields or function R on DSP APIs.

Do not bypass the guard or interpret the local tests as a successful UAT setup/reset integration.

Implemented caller behaviour
- POST .../dsp/api/password/v1/public-key sends only {"hashValue":"lowercase hex SHA256(six-digit nonce)"}.
- The provider stores the key against that hash; its modification API receives the original randomNumber.
- CM retains clientId, full closeId and requestId binding locally in the authenticated session.
  They are not added to the provider's public-key request.
- Internal APIC headers remain X-IBM-Client-Id, X-IBM-Client-Secret, Channel=BCO, UUID Message-Id.
- Only HTTP 200 with status=000000 and nonempty publicKey is accepted for key retrieval.
- HTTPS certificate/host checks stay enabled; no redirect or automatic retry.
- The low-level HTTP transport retains the configured .../password/v1/modification endpoint.
  The business adapter does NOT invoke it until the hash/reset contract is supplied.
- Status returns UNKNOWN with resetAllowed=false. It does not return NOT_SETUP/ACTIVE based on local history.
- Both setup/reset reject with DIGX_CZ_HTH_API_PASSWORD_009 before Code lookup/reservation/write/notification,
  including requests that would previously have been treated as USED replays.
- Code generation cannot safely auto-select SETUP/RESET; UNKNOWN fails with the same availability error.
- Opening the password form with UNKNOWN status shows the existing AC failure panel.
- Passwords/hashes are never logged or stored in CM. The three retired local password stores stay removed.
- HTH_API_PASSWORD_CODE remains for approval, 24-hour expiry and Code lifecycle; it is not a password-state cache.

Provider gaps — must be resolved before enabling setup/reset
1. Hash payload/storage (DSP owner + architect)
   AC and confirmed requirement: browser computes Base64(raw SHA256(UTF8(password))), encrypts it with DSP's key,
   and DSP stores the decrypted hash as-is.
   Existing PasswordApiServiceImpl.newPassword/modifyPassword instead call HashUtils.sha256(decrypted).
   HashUtils.sha256 returns lowercase HEX. Sending our Base64 hash would double-hash and change representation.
   Required: confirm the released hash-accepting API/version and exact hash encoding; do not change CM to transmit
   plaintext, re-hash again, or silently switch to hex to make the old endpoint appear to work.
2. Approved-Code reset (DSP owner + BA/architect)
   Existing A creates only when no active row exists. Existing M requires oldEncryptedPassword and validates it.
   CM reset has an approved Code and new password, not the old password.
   Required: provider-confirmed reset contract and authorization; do not use A as upsert, fabricate old credentials,
   add R ourselves or add an old-password UI field without an approved requirement change.
3. Credential status (DSP owner + architect)
   Neither of the two published endpoints returns whether clientId/full closeId already has a password.
   Required: supported status source/API for initial popup, SETUP/RESET Code purpose and reset availability.
   Code USED history, empty local tables and public-key success are not authoritative status.
4. Exact RSA OAEP parameters (DSP owner)
   Browser preparation currently uses SHA-256 for both OAEP and MGF1, empty label, RSA-2048.
   Provider code initializes Cipher with a transformation string only; MGF1 therefore depends on its provider default.
   Required: explicit OAEP digest + MGF1 digest + label and a non-production interop test vector.
   This delivery does not change shared DSP cryptography or claim existing-provider decrypt compatibility.
5. Internal APIC publication (DSP/APIC owner)
   Confirm the environment URLs/subscription and that the final provider contract is available there.
   Keep APIC credentials in environment configuration, separate from the business clientId.
