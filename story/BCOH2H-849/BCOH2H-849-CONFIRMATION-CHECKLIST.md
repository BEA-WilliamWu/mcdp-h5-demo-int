BCO 参考来自当前本地代码、SQL 和框架 JAR；实际启用哪些业务、数据库结构和运行参数，仍需与 UAT 核对。表中“未确认”表示暂时没有足够证据，不表示 BCO 一定没有。

spike 和 sample 只用于参考实现方式，不能据此确定本次业务范围。BA 确认“需要记录什么、何时记录、怎样理解数据”；架构师/TL 确认“从哪里取、在哪里保存、怎样实现”。

已确定：MTB 数据采集/保存失败只留必要日志，不自动重试、不补录，不新增补偿机制。这里的“保存失败”与“客户业务执行失败”不同；客户业务失败是否仍需留一条 MTB 记录，由 BA 确认。

| 确认项（直接描述需要明确的内容） | BCO 的做法 | 需要 BA 确认 | 需要架构/TL 确认 |
|---|---|---|---|
| **本次具体记录哪些业务和操作** | 按配置选择需要记录的业务；源码有用户管理、登录、安全、查询、支付等多类实现，并不是所有接口都会记录。是否启用以实际配置为准。 | 请逐项列出业务名称，以及创建、修改、删除、查询等哪些操作需要记录；哪些明确不做。不能只写“所有 HTH 业务”，也不能直接照搬 sample 或 Audit Log 清单。 | 将 BA 清单对应到具体接口、服务类和 task code；确认每项在哪个应用执行、由哪个团队修改，是否已有可复用的记录入口。 |
| **一次业务在什么时候产生记录** | 在业务返回结果或失败处理时进入 CRM；认证尚未完成时有跳过逻辑。审批响应会检查处理状态，另有普通响应和特定业务分支，不是全部只在最终审批后记录。 | 提交申请就记，还是最终审批通过并执行完成才记，或两个时点都记？多级审批是否每一级都记？拒绝、撤回、取消是否各记一条？请按业务分别说明。 | 找到对应处理阶段的调用位置，避免请求已受理但业务尚未成功就记为成功；避免业务入口、审批入口各记录一次造成重复。 |
| **客户业务成功或失败时，哪些结果需要记录** | 同时有成功及失败处理入口。通用结果使用 A/R，业务转换逻辑可覆盖；部分路径受配置和状态条件限制，不能认为所有失败都会记录。 | 是否记录业务失败、输入校验失败、认证/权限失败和系统异常？不同结果应显示什么状态，是否需要错误码？明确“客户业务失败”不等于“MTB 写库失败”。 | 确认从哪个响应字段判断真实结果，如何区分已受理、处理中、成功和失败；失败路径能否取得必需数据；业务事务回滚时如何按规则记录失败。 |
| **一次操作保存一条还是多条记录** | 通用路径通常写一条；部分内部转账另外写贷方记录，存在一次操作多条的情况。不同业务可自行拆分。 | 按一次操作、一名用户、一个账户、一项服务，还是每笔交易明细记录？一次修改多个账户/服务如何计算？批量部分成功时如何记录？ | 确定是否一张事件表即可，还是需要主表和明细表；确定每条明细的标识和关联方式，评估批量写入量。 |
| **每个业务需要保存哪些字段及其含义** | 公共方法取用户、渠道、日期等字段，业务转换逻辑补充或覆盖账户、金额、参考号等，再转换成数据库实体。sample 的列名不能代表所有业务必需字段。 | 提供逐业务 mapping：字段名称、业务含义、什么情况下必须有值、允许为空时如何表示、枚举/固定值。修改类业务是否需要旧值和新值？敏感内容是否只显示部分？ | 对每个字段标明来源：请求、响应、当前用户、数据库或配置；确定类型、长度、精度和转换规则，并核对字段是否在该时点可取得。旧值要在被覆盖前获取。 |
| **不同业务和处理阶段使用什么活动编码** | 活动码通常按 task 配置，部分业务代码会调整编码；银行管理员和企业端也可能不同。技术 task code 与对外活动码不是同一个概念。 | 与 MTB 接收方确认业务活动名称及编码；创建/修改、提交/审批、成功/失败是否分开，哪些可共用编码。 | 确认编码如何配置、是否与已有编码冲突、是否需要新增 task；保持 BCO 原有编码和配置不被覆盖。 |
| **记录中的用户究竟指操作人、目标用户还是审批人** | 公共 USER_ID 通常来自当前线程上下文/登录用户，包含 @ 时一般取前面的用户名；业务代码可以另行补充或覆盖信息。不能统一当成目标用户。 | 例如“管理员修改另一名用户，再由审批人批准”：需要保存哪几个人？是否分别有操作人、目标用户、最终审批人字段？用户名使用短名还是完整 closeId？ | 确认各身份从哪里可靠取得，尤其后台审批时不能把当前审批人误当原提交人；确认跨公司同名用户如何区分。 |
| **公司编号和实际交易账户分别记录在哪里** | 公共 ACCT_NBR 通常取当前业务公司 Party Code，部分业务会覆盖；部分交易另有借方、贷方账户字段。因此不能只看 ACCT_NBR 名字就认为是银行账户。 | 明确公司 Party ID、客户编号、实际借贷账户分别是否需要，以及每个字段代表什么；多公司/多账户操作应如何表达。 | 确认取值来源、字符串格式和长度，保留前导零；保证公司与账户关系正确，不混用不同类型编号。 |
| **数据是统一放新 HTH 表，还是有部分继续放 BCO 表** | 现有 CRM 链路主要写 DIGX_CZ_CRM_EVENT3_DETAILS，多种业务共用事件明细宽表，再由旧 batch 抽取。 | 明确下游是否要求将 HTH 与 BCO 数据分开、是否存在不同报表/接收用途；BA 不需要决定具体 schema 或 Java 类名。 | 最终决定新旧表边界、schema、数据源、写入应用、表结构和索引；避免 HTH 数据误进入旧 BCO 文件。核对真实 BCO DDL，不能用导出文件宽度代替数据库列长度。 |
| **本次是否必须异步保存，还是跟 BCO 一样直接保存** | 本地框架标准链路是直接调用 CRM 保存，没有另开 CRM 后台任务；如果业务本身在异步审批线程运行，CRM 就在那个线程保存。 | AC2 明确写了异步。若改为与 BCO 一样直接保存，需要 BA 确认调整 AC；若保留异步，确认可接受的落库延迟和故障时可能缺失记录的范围。 | 核对 UAT 框架是否与本地一致；评估同步耗时。若保留异步，选择独立、受控的后台执行方式，明确并发/队列上限、上下文传递和数据库事务；不因为异步就默认必须新增 JMS。 |
| **MTB 采集或写库失败后怎么处理** | 相关代码多为捕获异常后打印日志，未见该保存链路自动重试或补录；部分条件还会直接跳过。代码可能共用业务会话，捕获异常不一定保证主事务不受影响。 | **已定：不重试、不补录。** 评审记录说明此选择可能导致 MTB 缺少个别记录；若 AC 对完整性另有要求，由 BA 对齐口径。无需再要求设计补偿流程。 | 保留必要错误日志，避免记录密码等敏感输入；验证采集/写库异常的事务影响，不让记录失败意外改变主业务结果。不新增自动重试、outbox 或补偿任务。 |
| **如何避免同一次处理重复记录，以及用户重新操作怎么算** | 每次可生成新的 EVENT_ID；公共链路未见按请求号统一去重，部分业务用局部分支避免重复插入。主键不同仍可能代表同一业务。 | 不涉及补偿重放。只需明确：用户重新提交、重新查询，是一次新的业务事件，还是需要与前一次合并？这是统计口径，不是要求新增重试机制。 | **不新增补偿/重放框架。** 正常代码路径仍保证不重复调用；确认请求/交易参考号的关联方式。不能把“失败不补录”理解为可以重复插入，也不能把主键唯一当成业务去重。 |
| **日期时间取哪个时刻，以及使用什么时区** | 公共逻辑在组装时取系统当前时间，格式 yyyyMMdd/HHmmss，默认使用 JVM 时区；不一定是原申请或原交易发生时间。 | 需要提交时间、最终执行完成时间、记录生成时间中的哪几个？跨日审批按哪一天归类？是否统一香港时间？ | 核对服务器时区、日期列类型及转换规则。异步执行时提前保留业务发生时间，避免把后台实际写库时间误作业务时间。 |
| **数据保存多久、谁负责清理、预计数据量多大** | 已看到 batch 用 BATCH_PROCESSED_DATE 控制抽取，但当前未确认 BCO 统一保留期、清理任务或 UAT 实际容量。不能把“已抽取”理解为“可以立即删除”。 | 提供业务保留期限及历史查询/核对需要；尽量给出预计每日量、峰值业务量或现有统计。 | 与 DBA/运维确认容量、索引、清理责任及方案；区分待抽取与已抽取记录。是否需要清理开发及上线配置，明确归属哪个 story。 |
| **本次是否只做数据保存，不包含文件生成和传输** | BCO 有独立 GenTxnLog2CRM、批处理及后续传输流程。849 Description 描述最终文件目标，但当前 AC1/AC2 聚焦保存。 | 明确本次验收边界：是否排除 CSV、文件头尾、Control-M、SFTP、下游导入；需要时在 story 备注，后续由哪个 story 承接。 | 保持原 BCO batch 不变；本次数据设计保留将来抽取所需字段。后续再确认抽取条件、迟到数据、文件格式和传输配置。 |
| **怎样判断这个 story 已完成** | BCO 可以参考其对应业务生成的数据库记录，但并不存在一个适用于所有业务的统一 sample；配置和转换规则决定实际内容。 | 每个业务至少给出成功、需要记录的失败、多账户/多明细等验收例子，并列出预期条数和字段值规则；不要仅凭“表里有记录”验收。 | 提供接口到表的测试证据、异常路径测试和 BCO 回归结果。若 AC2 保留，证明后台执行；若调整为同步，记录性能验证。失败不补录也要验证，不只验证编译通过。 |

## 建议确认顺序

1. BA 先明确业务清单、记录时点、结果范围、条数、身份含义及字段 mapping。
2. BA 与架构师/TL 一起确认 AC2 和本次文件抽取范围。
3. 架构师/TL 据此确定调用入口、数据库设计、事务和执行方式；BA 不需要选技术类名或队列产品。
4. 将已确认的“不重试、不补录”及验收边界写回 story/技术设计，避免以后按不同理解验收。

本清单覆盖此前分析中的范围假设与可靠消息建议；早期文档提及的示例业务不代表已纳入 849。
